# Dish 9.3: Records and the whole journey

## 9.3.question
A DNS answer isn't just a name and an address. How does the same system tell you where to send email, or which server is in charge of a zone? And what happens if the question or its answer simply gets lost?

## 9.3.records
DNS stores typed resource records, each with a name, a type, a value, and a TTL. An A record maps a name to an IPv4 address. An NS record names the server authoritative for a zone. A CNAME maps an alias to its canonical name. An MX record names a domain's mail exchanger, with a preference. Notice that NS, CNAME, and MX values are hostnames, not addresses. So they may need another lookup, to find an address.

## 9.3.reliability
DNS usually runs over UDP, which recovers nothing. So reliability is built above it. Zones keep replicated servers. Clients use timeouts, retry, and try a different server. Replies are matched to questions by an ID. DNS can also use TCP, so UDP is common, not exclusive.

## 9.3.reliability-more
Walk through a failure. A resolver queries server A, and hears nothing. After its timer, it tries replica B, and it accepts a reply only if it matches the outstanding request. Repeating immediately to the same failed server would add load, without helping.

## 9.3.journey
We can tell the whole story in order, and there's a surprise in it. To reach the name, the laptop must query the resolver. But the resolver is remote. So before the DNS query can even leave, the laptop must ARP for its gateway. Then the frame goes to R1, carrying a packet to the resolver. The DNS answer returns. Only then can it send to the server, and a TCP connection can begin. The recap slide compresses that handshake. The classic form ends with a final ACK after the SYN and SYN-ACK.

## 9.3.insert
How does a new name enter this system? Say a startup called FooBar registers foobar.com. The registrar inserts two records into the dot com servers: an NS record saying that foobar.com is served by dns1.foobar.com, and an A record giving that server's address. That second one is needed, because otherwise you'd have to resolve dns1.foobar.com in order to reach the server that answers for foobar.com. On its own server, FooBar then adds an A record for www, and an MX record for mail.

## 9.3.dig
You can watch all of this with a tool called dig. A plain query prints three sections. The answer section has the record you asked for. The authority section names the servers responsible for that zone. The additional section gives those servers' addresses, which saves another lookup. An address shown under additional isn't necessarily the web server you asked about. Running dig with plus trace shows the entire walk from root to TLD to authoritative. And asking a TLD server directly, with recursion off, returns no answer at all, only a referral. That's an iterative reply, visible in plain text.

## 9.3.arb
The instructor's slides run this as a compact example: host A, router R, host B. A's address is 111.111.111.111, and B's is 222.222.222.222. A's mask says that B is off-subnet, so A uses ARP to learn R's near-side MAC. The frame runs from A's MAC to R's MAC, while the IP header reads A to B.

## 9.3.arb-2
R removes the frame, looks up B's prefix, finds B's MAC on the outgoing subnet, and emits a new frame from its far-side MAC to B's MAC. There it is again: the Ethernet destination is R on one link, and B on the other. The IP endpoints never change, in this ordinary trace with no NAT.

## 9.3.rule
There's no fixed order that says DNS comes before ARP. What is missing right now decides what happens next. The name's address is missing, so we need DNS. To reach DNS, we need the gateway's MAC, so we need ARP first. Discovery traffic has its own delivery dependencies.

## 9.3.pitfall
A frequent confusion. A CNAME is not an HTTP redirect. It's an alias inside DNS, so the resolver just looks up another name. The browser never gets sent to a new URL.

## 9.3.changed
Change three facts. Put the resolver on the laptop's own subnet. Make the DNS answer already cached. And then cut the link between R1 and R2.

## 9.3.predict
For each change, which steps disappear, and which still have to happen?

## 9.3.answer
A local resolver means the laptop ARPs for the resolver directly. A cached answer removes the hierarchy queries, but the web packet still needs its gateway and its routes. And a cut link? All of the laptop's DNS and ARP entries remain perfectly correct, yet delivery still fails, because R1's forwarding table is now wrong or incomplete. That table is the one piece we've taken for granted since the start. Who fills it in? That is routing.
