# Dish 6.2: From hub to switch

## 6.2.question
Plug eight machines into one box. Do they now have eight private conversations, or one big shared one? It depends entirely on what the box does with the bits.

## 6.2.hub
A repeater amplifies a weakening signal, so a LAN can stretch further. A hub is a repeater with many ports. Every bit arriving on one port is copied out of all the others. It reads no addresses. It stores nothing. So a hub with eight ports is still one wire, wearing a different shape. If A sends to B while C sends to D, they collide. The boundary that matters is the collision domain, not the number of boxes in the picture.

## 6.2.switch
Ethernet switching is different in kind. It receives a whole frame, reads the destination MAC address, and sends the frame only out the port that leads there. Now A to B and C to D run at the same time, through independent port pairs, with no collision at all. Each link has become its own little collision domain.

## 6.2.duplex
And with a private point to point link, a host can send and receive at once. That is a full-duplex link, and on it, collision detection has nothing left to do. Does that mean a switch never loses anything? No. If A and C both send to B, both frames need the same output. A switch has finite output rates and finite buffers, so frames must queue. We removed collisions, not contention.

## 6.2.modes
One choice remains: when does the switch start sending? Store-and-forward switching receives the entire frame first, and checks the CRC, so bad frames die here. Cut-through switching begins as soon as it has read the destination address. That saves some waiting, but it may forward a frame that later turns out to be corrupt.

## 6.2.rule
It helps to name exactly which delay is being removed. Reception time is frame length divided by rate. A 1500 byte frame at 100 megabits per second takes 120 microseconds just to arrive. Store-and-forward pays this at every switch.

## 6.2.pitfall
People often say a switch fixes everything a hub got wrong. It doesn't stop broadcasts from spreading, and a collision-free output can still queue and drop.

## 6.2.changed
Change the situation. Our frame's last bytes get corrupted on the way into the switch. And suppose the output port is busy, so the frame cannot begin leaving at once either.

## 6.2.predict
Under cut-through, does the bad frame reach B? And what does cut-through save if the output was busy anyway?

## 6.2.answer
With a free output, cut-through would already be sending when the corruption arrives, so a bad frame can reach B. With a busy output, the frame has to wait anyway, so the savings shrink. Store-and-forward would have discarded it. There is still a gap in the switch story. It sends a frame only out the right port. But how could a box you just took out of the packaging possibly know which port is right?
