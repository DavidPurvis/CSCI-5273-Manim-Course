# Dish 10.4: MPLS labels

## 10.4.question
Every router on a path repeats a longest prefix match, for the very same packet. And all traffic to one destination follows the shortest path, even when another route has spare capacity. Could we set up a path in advance, and just follow it?

## 10.4.label
That's what MPLS does. At the edge of the network, an ingress router classifies the packet, and pushes a short label in front of the IP header. Routers inside read only the label, and look it up in a small exact table. The label says which prepared path this packet is on. The last router pops the label, and ordinary IP takes over.

## 10.4.swap
Labels only have local meaning. Label 17 reaches R2, whose table says: incoming 17, swap to 42, and send on this interface. Then R3 sees 42, and its table says to pop. Each router picks its own numbers, so the label changes at each hop while the path stays fixed. Does that remind you of something? The label behaves just like the yellow envelope. Only the IP header stays the same throughout.

## 10.4.signal
Who installed those table entries? Signaling. Before any data flows, messages travel along the chosen path, setting up state at each router. The lecture names RSVP, and for MPLS traffic engineering, the specific extension is RSVP-TE. Because the path is explicit, an operator can steer some traffic away from the shortest route, onto spare capacity. That is traffic engineering.

## 10.4.te
See what that buys. With ordinary IP, two packets for the same destination take the same route from any given router, because they match the same prefix. With labels, an ingress router can place them on different prepared paths. The original motive for MPLS included faster lookup. Today, traffic engineering is the bigger reason.

## 10.4.rule
Remember what a label path is, and what it is not. It's prepared forwarding state. It doesn't by itself reserve bandwidth, and it doesn't make delivery reliable. Something must still decide what state to install, and that's the control plane again.

## 10.4.laptop
Back to our laptop's packet. At every router on the way to the server, it now finds a table entry, built from a shared map, from neighbors' distances, or from paths. Where MPLS is in use, it may even carry a label for part of the way. The packet itself never knew any of this happened.

## 10.4.pitfall
A label alone doesn't reserve anything. It's just how a router finds the next step. Reserving capacity takes signaling, and not every MPLS deployment uses it.

## 10.4.changed
Change the question. R2's own table reuses label 17 for a totally different path, on another interface. And a packet with label 99 arrives at R2, where no entry exists.

## 10.4.predict
Is reusing 17 a conflict? And can the router just fall back to searching the label space for the packet with 99?

## 10.4.answer
Reuse isn't automatically a conflict, because labels are local, and each entry's scope is defined by its table. Different routers routinely reuse the same number. A label with no matching state has no installed instruction, so it has no valid forwarding action. State has to exist before it can be used. And that raises this chapter's biggest question. We've treated every table as correct and complete. What really happens in the seconds after a link fails?
