# Dish 9.1: Getting an address and a neighbor

## 9.1.question
Rewind to the moment the laptop wakes up. It holds one thing: its burned-in MAC address. It has no IP address, no mask, no idea where the router is, and no way to translate a name like www.example.test. How does it get from knowing nothing to sending a packet?

## 9.1.identifiers
It needs three kinds of identifier, because they answer three different questions. A name is for people, and it can stay the same when a service moves. An IP address says where an interface sits in the topology. A MAC address gets a frame across one local link. Each translation between them is a separate protocol. That indirection is what lets a server change its address while its name stays fixed.

## 9.1.habit
The habit to build. Before naming a protocol, state the missing fact. I need my own address and my gateway: that is DHCP. I need the MAC address of my next hop: that is ARP. I need the IP address behind a name: that is DNS.

## 9.1.bootstrap
Start with the bootstrap problem. The laptop needs to ask a server for an address. But it has no address to send from, and it doesn't know where any server is. There is a way out of that circle. Local broadcast reaches everyone on the LAN, with no configuration at all. So DHCP begins with a shout.

## 9.1.dora
Four messages follow. Discover: is any DHCP server out there? Offer: a server proposes an address, say 192.0.2.10, along with a mask, a gateway, a DNS resolver, and a lease time. Several servers might offer. Request: the client announces which offer it chooses. ACK: that server confirms. Only after the ACK does the client begin using the address. An offer alone is just a proposal.

## 9.1.config
Look at what the laptop now knows. Its address, 192.0.2.10, with a slash 24 mask. Its gateway, 192.0.2.1. Its resolver, 198.51.100.53. It knows what counts as local, and where to send everything else. Yet it still does not know the gateway's MAC address. Knowledge arrives in stages, not in one magic connected moment.

## 9.1.lease
Why does the address come with a lease? Suppose a laptop crashes, or simply leaves. It never says goodbye. If allocations were permanent, the pool would slowly drain. With a lease, the allocation expires unless it is renewed. This is called soft state: information that disappears on its own unless refreshed. Failed machines clean up after themselves, by doing nothing. A reservation is different. An administrator configures a fixed address for a particular machine, and the server hands it out centrally each time.

## 9.1.arp
The laptop wants to send through its gateway, 192.0.2.1. A frame needs a MAC address, and it has only an IP address. So it checks its ARP cache. Empty. It broadcasts: who has 192.0.2.1? Every machine on the LAN hears. Only R1 replies, directly: that's me, and here is my MAC. The laptop caches that mapping for a while. Another soft state table.

## 9.1.two-tables
ARP resolves only the next local hop, never the whole path. And don't confuse it with the switch's table. The host's ARP table maps IP to MAC. The switch's table maps MAC to port. Both changed during that exchange, and neither replaces the other. The rule is: route first, resolve the next hop's MAC second, transmit third.

## 9.1.pitfall
Keep these lookups apart. ARP doesn't resolve a hostname, and DNS doesn't choose the Ethernet destination. DNS maps a name to an IP. ARP maps an IP to a MAC.

## 9.1.changed
Change the target. The laptop now wants to send to the DNS resolver, 198.51.100.53. Apply the slash 24 mask to both addresses. 192.0.2.0 is not 198.51.100.0.

## 9.1.predict
Which IP address does the laptop put in its ARP request?

## 9.1.answer
It asks for the gateway, 192.0.2.1, never for the resolver, because ARP cannot cross a router. If the resolver were on the same subnet, at 192.0.2.53, it would ARP for the resolver directly. So the mask chooses the next hop, and the next hop chooses the ARP target. The laptop can now reach its resolver. But what does a resolver actually do? How can any system answer for every name on Earth?
