# Dish 13.2: Who wants the stream?

## 13.2.question
A source wants to send one 10 megabit per second stream to three receivers. All three sit behind the same first link. Must that link really carry three identical copies? And how would the network even know who wants the stream?

## 13.2.unicast
The simple answer is iterated unicast. Just send a separate copy to each receiver. It needs no network support at all. But on the shared link, that's 3 times 10, or 30 megabits per second, all carrying the same bits.

## 13.2.unicast-more
Scale it up. A one megabyte file sent separately to 100 receivers makes the sender transmit 100 megabytes. If every copy crosses the same upstream link, that link carries all 100.

## 13.2.multicast
IP multicast does better. The source sends one copy, addressed to a group, and routers replicate it only where paths diverge. The shared link carries just 10 megabits per second. The saving is on the shared edges. There's still forwarding work at each branch. And notice the difference from anycast. Anycast reaches one of many. Multicast reaches all who are interested.

## 13.2.address
What goes in the packet? The sender keeps its ordinary source address. The destination is a group address, drawn from 224.0.0.0/4. That address names no single machine, only an audience. A sender doesn't have to be a member. And the group's membership can change at any time.

## 13.2.address-more
A concrete example. A sender at 192.0.2.10 sends to group 239.1.1.1, and two receivers join that group. The packet's source stays 192.0.2.10, and its destination is 239.1.1.1. The source never becomes the group address.

## 13.2.overlay
What if routers don't support multicast? Overlay multicast builds the distribution tree among the end hosts themselves, using ordinary unicast. Each host receives the stream, and forwards it to a few others. It needs no router support. But overlay paths can cross the same physical link repeatedly, and forwarding uses up the hosts' upload capacity.

## 13.2.overlay-more
Picture it as a tree of hosts. The source sends to two peers, and each of them sends to two more. Seven recipients fit in three levels, and no router needs to know anything about the group.

## 13.2.igmp1
Who's interested? IGMP handles this on the local network, between hosts and their directly attached router. The router sends a query: any members out there? Hosts reply with reports. Here's a clever trick. H1 and H2 both want group G. Each picks a random delay, say 2 seconds and 6 seconds. H1's timer fires first, and it sends its report to the group itself. H2 hears the report, and cancels its own. Why? Because the router only needs to know that someone on this LAN wants G, not who, or how many. In version 1 there's no leave message. Membership simply expires when reports stop.

## 13.2.dest
The slides speak loosely here, so let's be exact. In version 1, queries go to the all-hosts group, and a report goes to the group being reported. That's how H2 hears H1's report. Both are limited to the local network with a TTL of 1.

## 13.2.igmp23
Version 2 adds an explicit leave. When a host leaves, can the router stop forwarding at once? No. Another host on the LAN may still want the group. So the router sends a group-specific query to check. If H2 still cares, its report keeps the branch alive. Version 2 also adds querier election. Version 3 adds source filtering, so a host can say: I want group G, but only from source S.

## 13.2.timer
A timer detail, with a clarification. The slide computes a timeout as 2 times the sum of 125 and 10, which gives 270 seconds. The standard's default formula, in RFC 2236, is 2 times 125, plus 10, which gives 260 seconds. If a question supplies the slide's formula, use it, and say so. Just don't quietly swap one for the other.

## 13.2.snoop
Finally, what about the switch? An ordinary switch floods multicast out every port. IGMP snooping lets it listen in on these membership messages, and deliver only to ports with interested hosts. So keep the scope clear. IGMP is about one local network. It doesn't build the tree between routers.

## 13.2.snoop-more
Say only one port has a receiver for a group. A snooping switch sends that group's traffic toward that port, and toward its router ports, rather than every access port. This is separate from unicast MAC learning, because it comes from reading membership messages.

## 13.2.pitfall
Keep the scope straight. IGMP tells the last router which groups are wanted on its LAN. It doesn't compute the tree between routers. That's a multicast routing protocol's job.

## 13.2.changed
Change the numbers. A 5 megabit stream, three receivers behind one shared link, with report delays of 2, 5, and 8 seconds.

## 13.2.predict
What's the load on the shared link, with unicast versus multicast? And how many reports does the router actually hear?

## 13.2.answer
Unicast loads the link with 15 megabits per second. Multicast with 5. And the router hears only one report, at 2 seconds, because the others suppress theirs. So local interest is known. But how does the data cross many routers, to reach all those interested networks? We need a tree. And it turns out the word tree can mean several different things.
