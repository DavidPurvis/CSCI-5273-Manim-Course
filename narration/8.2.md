# Dish 8.2: The longest match

## 8.2.question
R1 holds a table of prefixes. Because prefixes can nest, one destination can match several entries at once. Which one should win? And how can a router decide this in a few nanoseconds, a few million times every second?

## 8.2.table
A router's table with three entries. 201.10.0.0/21 goes out output A. Inside that block, 201.10.6.0/23 goes out output B. And 0.0.0.0/0 goes out output C. Those entries overlap on purpose. The slash 21 is an aggregate, the slash 23 is an exception carved out of it, and the slash 0 is the fallback.

## 8.2.match
A packet arrives for 201.10.6.17. To test a route, mask the destination with the route's prefix length and compare. Under the slash 21 mask it matches. Under the slash 23 it also matches. And slash 0 matches everything. Three matches. The rule is longest prefix match. Choose the match with the most network bits, because it is the most specific claim. So the slash 23 wins, and the packet leaves on output B.

## 8.2.more
201.10.4.8. Its third byte, 4, lies within the slash 21, which covers 0 through 7, but not within the slash 23, which covers only 6 and 7. So output A. And 203.0.113.8 matches only the fallback, so output C. A route's position in the list does not matter. Neither does any metric from an unrelated route. Only prefix length decides among installed matches.

## 8.2.bitlevel
Let's see this at the level of bits, because that's what the hardware does. Write the destination, 201.10.6.17, above the route's network, 201.10.6.0. Under a slash 23, only the first 23 bits count. Compare them. Every one matches, so this route matches. Whatever's to the right of the boundary doesn't matter. Now compare 201.10.4.8 against that same route. Look at the third byte. 4 is 00000100, and 6 is 00000110. They differ in bit 23, inside the prefix. So that's no match, and that second packet falls through to the shorter route.

## 8.2.budget
The speed problem. Scanning every route is far too slow. On a 10 gigabit link with 64 byte packets, there are about 19 and a half million packets each second, which leaves 51 point 2 nanoseconds per packet. That calculation leaves out Ethernet's physical overhead, so treat it as a budget illustration. But the conclusion holds. There is no time for a linear scan.

## 8.2.trie
One answer is a trie, a tree you walk one address bit at a time. Follow the destination's bits down from the root. Whenever you pass a node holding a route, remember it. If the path dead-ends deeper down, you still have the last route you remembered. That is why a failed deep branch does not lose the earlier match. A Patricia trie compresses long chains with no branching, and multi-bit nodes trade memory for fewer steps.

## 8.2.cam
The other answer is hardware. Ordinary memory takes an address and returns the content. Content-addressable memory does the reverse. Give it a key, and it compares against every entry at the same time. A plain CAM needs exact matches, which suits MAC tables. Prefixes have don't care bits. TCAM adds a third state, so a stored entry can say these bits must match, and these do not matter. Several entries can still match, so hardware priority must favor the longest prefix.

## 8.2.general
Once you can match bit patterns, why stop at the destination? Generalized forwarding matches on selected header fields and applies a configured action, such as forward, drop, or rewrite. That connects back to software-defined networking. Whether by prefix or by general match, the principle holds. Control installs the rules. The data plane applies them, one packet at a time.

## 8.2.pitfall
The classic slip is stopping at the first match, or taking the lowest cost. In a table, order doesn't matter. In a trie, you keep walking, and remember the longest valid prefix so far.

## 8.2.changed
Add a route. An operator installs 201.10.6.16/28 going to a new output, D, and a metric says the slash 21 is an excellent path. Our first packet, 201.10.6.17, comes back through.

## 8.2.predict
Which output does it take now? And what would 201.10.6.33 do?

## 8.2.answer
The slash 28 covers 201.10.6.16 through 31, so 201.10.6.17 goes to D. The metric never entered into it. And 201.10.6.33 is outside the slash 28, so the slash 23 catches it, output B. Finding the output is only half of forwarding, though. The packet still has to physically cross the router. So let us go inside.
