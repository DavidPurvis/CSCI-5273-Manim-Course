# Dish 11.1: When a link fails

## 11.1.question
A backhoe cuts a fiber between two routers. A moment before, every table was correct. A few seconds later, every table will be correct again. So what happens to our laptop's packets during those few seconds? The answer shows that correct before and correct after does not mean safe in between.

## 11.1.laptop
Picture our laptop's video call, running happily through R1 and R2. The packets keep coming every few milliseconds, whether the tables are ready or not. So a failure isn't an abstract event. It happens underneath traffic that's already moving.

## 11.1.causes
First, what kinds of change are we talking about? Some are planned: maintenance that shuts down a link, or traffic engineering that changes a weight. Others aren't: a fiber cut, a power failure, or crashing software. Keep this separate from a different problem we'll reach later. A new route to the same location is a routing change. A host moving to a new location is mobility. Here, the destination stays put, and the network underneath it changes.

## 11.1.detect
First, how does anyone even find out? Sometimes the hardware reports a dead link. Often routers exchange periodic hello messages, and declare a neighbor dead after a few are missed. That leaves a real tension. A short timer finds failures quickly, but it costs more traffic and processing, and it can raise false alarms, since a delayed hello looks exactly like a dead neighbor. A long timer is calm, and slow.

## 11.1.stages
Detection is just the start, and it's local. Everybody else must then be told. Routing convergence is the whole transition, and it has four stages. Detect the change. Spread the news. Compute new routes. Install them in forwarding tables. If those take 30, 10, 5, and 15 milliseconds in sequence, the total is 60 milliseconds. Real stages can overlap, and each router's clock runs differently. But name the stages, before you blame the algorithm.

## 11.1.blackhole
Watch the packets. A forwards traffic for D to B, and B forwards to D. The link from B to D fails. B knows, but A hasn't heard. A keeps sending to B, on its old and perfectly reasonable route. B has nothing usable, and those packets vanish. That's a forwarding blackhole. Note that A has not computed anything wrong. It's just working from old information.

## 11.1.loop
B computes a new route for D. It goes back through A, then C, then D. And B installs that first, while A still points to B. So look at what happens now. A sends the packet to B. B sends it back to A. They bounce it between them. The old configuration had no loop. The new configuration has no loop. The mix of the two does. This is a transient forwarding loop. It isn't specific to any one protocol, and it can happen with link state, whenever routers install their changes at different times.

## 11.1.consequences
What does IP's TTL do here? It eventually kills the looping packet, but it doesn't save it, and until then, the loop eats up link capacity. Other packets may arrive out of order when old and new paths have different delays. So an application can suffer, even if a perfectly good alternate path exists the whole time.

## 11.1.improve
To improve convergence, work stage by stage. Detect faster. Send control messages promptly. Compute incrementally. Install changes efficiently. And keep the principle in mind: a faster processor cannot make up for waiting minutes to declare a neighbor dead. Find the slowest stage first.

## 11.1.pitfall
A tempting thought: both the old tables and the new tables are correct, so no harm done. But correct before and after protects nobody in between. Packets can vanish or loop during the transition.

## 11.1.changed
Change the install order. Same failure, same routers, but this time A installs its new route first, and goes through C directly. Then B installs its route, by way of A.

## 11.1.predict
With that order, is there a loop? Is there still a blackhole, at any moment?

## 11.1.answer
No loop forms, because A no longer sends to B. Traffic from A goes straight to C and D. Packets that reach B in the gap before it installs can still be lost, so B's own blackhole lasts until it updates. Ordering changes which disruption you get. These problems come from timing, and they pass quickly. But one protocol family can make things far worse: nobody gets told the truth for a very long time.
