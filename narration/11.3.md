# Dish 11.3: BGP that won't settle

## 11.3.question
Path vector carries the whole path, so a router can spot a loop at once, and count to infinity disappears. Does that mean convergence is solved? There are two remaining problems. It can be slow in a new way. And even worse, with some policies, it may never settle at all.

## 11.3.liveness
First, how do BGP neighbors notice that one of them has died? BGP runs over a TCP connection, and TCP alone won't tell you that an idle peer has vanished. So neighbors send keepalive messages. In the slide's example, a keepalive goes every 60 seconds, and the hold timer is 180 seconds. If nothing arrives for that long, the session is declared dead. Every route learned over it is then invalid. So just detecting one failure may take three minutes.

## 11.3.explore
Suppose destination 0 disappears entirely. Follow AS 2 as the news spreads. It's been using the direct path, 2, 0. That gets withdrawn. But it remembers an alternative through AS 1: 2, 1, 0. It looks fine, it's loop-free, and it's false, since AS 1 simply hasn't heard yet. Then that's withdrawn too. So it tries 2, 3, 0, which is also stale. Next 2, 1, 3, 0, longer still. Only after all of those does it finally have no route. This is path exploration. Each candidate seems reasonable locally, and each fails in turn. Every step also causes more update messages.

## 11.3.exploration-cost
Why doesn't that settle faster? Each router must first hear about the failure of what it's using, then choose its next best candidate, and advertise that. Those messages are limited by timers, so that routers aren't flooded with updates. So each wrong candidate can take a while to be discovered. Also, not every BGP change is a hardware failure. Import and export policy changes, resets of sessions, and persistent instability all make routes change too.

## 11.3.spp
The deeper problem. Each network ranks paths by its own policy. Do those independent choices always fit together? To study this, there's a clean model called the stable paths problem. Each node has a ranked list of permitted paths to destination 0. A path is available only if the next hop is actually using exactly the rest of that path. A stable assignment gives every node its best available path, all at the same time.

## 11.3.solve
Solve the instructor's instance. Node 3 has only one permitted path, 30, so it uses it. Node 1 prefers 130, and since 3 uses 30, that's available, so node 1 uses 130. Node 2 prefers 210, which requires node 1 to use 10. But node 1 uses 130, so that's unavailable, and node 2 falls back to 20.

## 11.3.solve-2
Node 4 prefers 420, and node 2 does use 20, so 420 works. Node 5 allows only 5210. That needs node 2 on 210, which it isn't. So node 5 has no path, even though it's physically connected to node 2. The slide asks two questions. Will node 1 use a direct path? False. Does node 5 have a path? False.

## 11.3.multi
That instance has exactly one solution. Others don't. Take two nodes, each preferring to reach the destination through the other. Node 1 likes 120 best, and node 2 likes 210 best. There are two stable outcomes. Node 1 goes through node 2, while 2 goes direct. Or the reverse. Which one you get depends on who speaks first. Same policies, same links, different result.

## 11.3.gadget
Three nodes in a ring. Each prefers the path through its clockwise neighbor, and each will otherwise go direct. Try to settle them. If node 1 goes direct, node 2 can use its favorite, through node 1, and so node 2 is not direct. Then node 3 can't use 320, and goes direct. But then node 1 can use 130, its favorite, and is no longer direct. That undoes node 2's choice. And round it goes. An exhaustive check of every assignment finds no stable solution at all. No link failed. Policies alone keep routes changing, forever. That's policy oscillation.

## 11.3.laptop
For our laptop, all of this shows up as a stall or a gap. Its video freezes for a moment, and then recovers. The laptop did nothing wrong, and neither did its server. The network was changing its mind, or couldn't settle it.

## 11.3.pitfall
The trap with path exploration. A path with no AS loop can still be stale. No loop is a much weaker claim than, this path is still available now.

## 11.3.changed
Change one line of policy. Node 3 decides it will no longer prefer the path through node 2. It now ranks going direct first, with 320 second.

## 11.3.predict
Does that single change produce a stable solution? Work it out starting from node 3.

## 11.3.answer
Yes. Node 3 uses 30, and never moves. So node 1's favorite, 130, is always available, and node 1 uses it. Node 2 then can't use 210, and so it goes direct, on 20. Everyone's happy, and nothing changes. One local preference broke the cycle. So the trouble isn't BGP's messages, it's the combination of rankings.
