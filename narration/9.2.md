# Dish 9.2: Finding a name

## 9.2.question
The browser has the name www.example.test. It needs an address. There are billions of names, changing constantly, owned by millions of organizations. Could one file hold them? Could one giant server answer them all?

## 9.2.rejected
The two obvious designs fail. A hosts file downloaded by everyone would be enormous, and always stale. One central server would be a single point of failure, a traffic bottleneck, and far away from most people. So DNS distributes the database, by splitting up responsibility.

## 9.2.hierarchy
Names form a tree, read from the right. The root delegates to top-level domain servers, such as dot test or dot com. Those delegate to authoritative servers for each organization's zone. A zone is a piece of the tree under one administration. Nobody holds everything. Each server only knows who to ask next. By the way, you may hear about 13 root servers. That is 13 named identities, A through M, each deployed as many physical instances around the world.

## 9.2.lookup
Follow one lookup with empty caches. The laptop asks its resolver: please find this name for me. That is a recursive query. It asks the server to do all the work. The resolver then asks the root. The root doesn't know the answer, but it gives a referral: ask the dot test servers. The resolver asks those, and gets another referral: ask example dot test. It asks that authoritative server, and gets the answer. Those are iterative queries. Each returns an answer or a pointer, and leaves the next step to the asker. The result returns to the laptop: 203.0.113.80.

## 9.2.rule-rec
One lookup uses both styles. The client to resolver request is recursive. The resolver's walk down the tree is iterative. An exam question that asks which one DNS uses is really asking, which hop?

## 9.2.cache
Doing all that for every request would crush the root. So the resolver caches. Each answer carries a TTL, in seconds. Store a record with TTL 300 at noon, and it can be reused until 12:05. Now the catch. If the real address changes at 12:01, the cache keeps giving out the old one for four more minutes. A shorter TTL narrows that window, at the cost of more lookups. That's a straight trade between freshness and load. Resolvers also cache referrals, so most queries never touch the root.

## 9.2.negative
Resolvers remember failures too. Negative caching stores the answer that a name doesn't exist. Repeated typos, like www dot example dot tesst, then fail quickly, instead of walking the tree each time. There's a downside. A brand new name might stay hidden behind an unexpired negative answer. And don't confuse a genuine no such name result with a mere timeout.

## 9.2.negative-more
Imagine someone keeps typing a name with a letter missing. Once the resolver learns that name doesn't exist, it can fail those requests quickly, until the negative result expires. A timeout is different. It only means no answer arrived, not that the name is missing.

## 9.2.pitfall
Same word, different meaning. A DNS TTL is a cache lifetime, in seconds. An IP TTL is a hop limit. And a switch's aging timer is different again.

## 9.2.changed
Change the state of the cache. A second laptop on the same LAN asks for www.example.test 4 minutes after the first one. The resolver stored the record with TTL 300.

## 9.2.predict
How many queries does the resolver send to the hierarchy? And what about a third laptop at 5 minutes exactly?

## 9.2.answer
At 240 seconds the cache is still valid, so zero queries leave the resolver. At 300 seconds the entry has expired, so it must ask again, though a cached referral could skip the root. Caching removes hierarchy traffic only. The packets to the web server still need routes and frames. Next, let us see what else this database holds.
