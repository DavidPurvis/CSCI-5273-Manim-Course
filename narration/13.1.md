# Dish 13.1: One address, many servers

## 13.1.question
Our laptop has been talking to one server. But a popular service runs in many locations. DNS could return different addresses, but what happens if one of those servers fails? The laptop's cache keeps handing out the dead address until the TTL runs out. Could one single address lead to several servers, so a failure needs no new DNS answer at all?

## 13.1.laptop
So far, our laptop has sent to exactly one server. But when it looks up a popular name, which of a thousand servers should answer? And when it joins a live stream, what if a million other laptops want the same bits? The destination is about to stop meaning one machine.

## 13.1.dnslimits
See the limit first. A DNS answer may hold several A records, for load balancing and failover, each one valid for 300 seconds. If a server fails, clients can hold on to its address for that long. A very low TTL puts extra load on DNS, and browsers may cache addresses regardless. And what if the DNS server itself is the thing that fails? We can't use DNS to fail over DNS.

## 13.1.announce
It can, and it takes no new protocol. Give two server instances the same address, 10.0.0.1, and let both locations announce it into routing. Routers simply see two routes to one destination. Router 1's table lists 10.0.0.1 through router 2 at distance 1, and through router 3 at distance 2. It chooses the closer one, just as it would for any route. That's IP anycast. One destination, delivered to one selected instance.

## 13.1.failover
Instance A fails, and its route is withdrawn. The client does nothing. It keeps sending to the same address. Router 1 falls back to the remaining route, and packets now reach instance B. There's no new DNS answer, and no client change. But failover isn't instant. It still waits for health detection, and routing convergence. And ordinary routing knows nothing about server load, or whether the program behind a live route is actually healthy.

## 13.1.rule
Here's the rule. Anycast means one of many, and routing picks which one. DNS still says just one thing, www.server.com is 10.0.0.1, and that answer stays true. Be aware that the slide's slash 32 is an internal toy example. Whether the wider Internet accepts a prefix that specific depends on routing policy.

## 13.1.pitfall
The slide's warning is easy to overread. Anycast isn't banned for TCP. The real issue is that a flow might shift to an instance without its connection state.

## 13.1.changed
Use anycast for something long-lived. A client has an open TCP connection to instance A. Routes shift, though nothing failed, and the next packet is delivered to instance B.

## 13.1.predict
What does instance B do with that packet, and why?

## 13.1.answer
B has never heard of this connection. It has no state for it, so the connection can break. That's the real meaning of the slide's warning. The problem is lost connection state, and anycast isn't flatly incompatible with TCP. Stable routing and careful service design make it workable. In fact, the DNS root servers we met earlier are deployed this way: 13 identities, with many anycast instances. Anycast picked one receiver out of many. Next, what if we want all of them?
