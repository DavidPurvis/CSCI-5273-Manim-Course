# Dish 13.4: RPF and PIM

## 13.4.question
A router receives a multicast packet. If it floods the packet out every port, loops and duplicates will multiply, and we saw how badly that ends on Ethernet. How can a router decide whether to accept a packet, without any tree having been computed?

## 13.4.rpf
An elegant trick. Look at where the packet came from, and ask: if I were sending a packet back to this source, which port would I use? If the packet arrived on that port, it probably came along the shortest path. Accept it, and forward it out the other ports. If it arrived anywhere else, it's a duplicate that wandered around another branch. Drop it. That's reverse path forwarding. Say router X reaches source S through port 1. A packet from S arriving on port 1 passes. A copy arriving on port 3 fails.

## 13.4.prune
RPF alone still sends data everywhere, as a broadcast with no duplicates. Let's narrow it. Truncated reverse path broadcasting skips a leaf LAN when IGMP says no members exist there. That removes only the last hop. Reverse path multicasting goes further. If a router has no local members, and none of its downstream routers want the data, it sends a prune upstream. Prunes propagate, so entire uninterested subtrees drop out.

## 13.4.dense
PIM, protocol independent multicast, is the standard router protocol. It's called independent because it reuses whatever unicast routing is available. PIM dense mode is the approach we've just seen. Flood, then prune. Everything is forwarded unless a branch opts out. That's sensible if most networks want the data, but wasteful if very few do. Prunes also expire, so the flooding comes back periodically.

## 13.4.sparse
When receivers are rare, we flip the default. In PIM sparse mode, nothing flows until someone asks. Everyone agrees on a meeting point for the group, called the rendezvous point, or RP. A receiver's designated router sends a star comma G join toward the RP, creating a shared tree. Data then flows only along the branches that joined. The slide's phrase, CBT, source based, is shorthand. What actually happens is that sparse mode starts with this shared tree.

## 13.4.register
A source appears. Its designated router doesn't know the receivers. It only knows the RP. So it wraps the first data packets in a PIM Register message, and unicasts those to the RP. That's encapsulation again. The RP unwraps them, and sends them down the shared tree. Then the RP can set up native forwarding from the source, so that encapsulation is no longer needed.

## 13.4.register-more
Why wrap it at all? The source's router knows only the RP, and the RP hasn't built a path back yet. So Register is a bootstrap. The RP can unwrap each packet and send it down the shared tree, while native forwarding toward the source is being set up. A Register is not a join, and it's not a host's IGMP report.

## 13.4.spt
But there's a problem: the RP might be far out of the way. Say source to RP costs 8, RP to receiver costs 7, and the direct path costs only 4. The receiver's router can now join toward the source, using S comma G. Once data arrives on the new path, it prunes this source from the RP branch. The cost drops from 15 to 4, a saving of 11. The group address stays the same. This is called SPT switchover. Start with a shared tree for easy discovery, then optimize.

## 13.4.rule
There are two axes. Dense mode says: forward by default, and prune. Sparse mode says: send nothing until joined. And on any tree, RPF checks the upstream direction, while pruning trims the downstream outputs. IGMP tells the last router who is interested, and PIM connects the routers.

## 13.4.compare
Set the two modes side by side. Dense mode starts broad, and shrinks. It needs no meeting point, but it pays with periodic flooding, and state in routers that have no interest. Sparse mode starts empty, and grows. It needs an RP, and it starts with possible detours, but quiet parts of the network never hear about the group at all. IP multicast is still best effort throughout, and neither mode makes it reliable.

## 13.4.laptop
For our laptop, joining a stream is simple. It sends one IGMP report to its local router. Everything else, the joins, the RP, the tree, happens in routers it never hears about. And if it stops listening, those branches get pruned away.

## 13.4.pitfall
A group address has no location to route toward. The reverse path check asks about the source, or the tree's root: would I reach it through the port this packet came in on?

## 13.4.changed
Change the geography. Suppose the RP sits right next to the path. Source to RP costs 2, RP to receiver costs 3, and the direct path costs 5.

## 13.4.predict
What does a switchover save now? And is the RP then a hot spot, or a bargain?

## 13.4.answer
Nothing at all. 2 plus 3 equals the direct 5. Switching would add state, for no shorter path. So the shared tree is not inherently bad. The cost of the detour depends on where the RP sits. That finishes our wired story. Packets have reached one host, one of many, and all who asked. But now the laptop unplugs from its wire, and all those assumptions about who can hear whom begin to fall apart.
